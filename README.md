# CyberLeague — конфиги, прицелы и Twitch (обновление)

**Два независимых парсера** (`scripts/parsers/`), запуск — `node scripts/update-cs2-content.js` (в GitHub Actions — автоматически):
- **Конфиги — CYBERSHOKE** (`cybershoke-configs.js`). Источник: публичный JSON страницы https://cybershoke.net/ru/configs (`POST /api/api/v1/config/list`, группы «PRO-игроки» и «Таланты», по 100 записей на страницу). Берутся: ник, аватар Steam, отметка «подтверждён», дата обновления, число скачиваний, описание и все переменные конфига (мышь, прицел, viewmodel, HUD, радар, звук, прочее). Ссылка «Скачать» ведёт на страницу конфига игрока на CYBERSHOKE. **DPI, разрешение, команду и оборудование источник не публикует — на сайте их нет.** Обновление — раз в 6 часов.
- **Прицелы — CS-CONFIG** (`csconfig-crosshairs.js`). Источник: публичные страницы категорий «PRO-игроки» и «Стримеры и ютуберы» (https://cs-config.com/crosshair-cs2/). Берутся: ник, категория, код прицела, дата, ссылка на исходную страницу. Быстрое обновление — раз в 12 часов (только новые страницы), полный обход — раз в неделю. Команд у прицелов источник не указывает.
- Дубли: один игрок — одна запись (ключ — Steam ID у конфигов, ник без учёта регистра у прицелов); новая версия прицела становится основной, старые — в «Предыдущие версии». Существующие записи обновляются, исчезнувшие из источника не удаляются (ссылки не ломаются).
- Сбой источника не ломает сайт: остаются последние данные, ошибка пишется в `assets/js/data/cs2/status.json`. CAPTCHA и авторизация не обходятся; при 429 — пауза и повтор.
- Ручной импорт прицелов, если источник станет недоступен: `node scripts/update-cs2-content.js --import=файл.json`.
- Данные: `assets/js/data/cs2/configs.json` (лёгкий список), `configs/<steamid>.json` (полный конфиг — грузится только на странице игрока), `crosshairs.json`. Браузер не обращается к источникам.

**Страницы:** `/configs` и `/crosshairs` — поиск по нику, фильтр по категории, сортировка, пагинация (48 на страницу, состояние в адресе). `/config/<ник>` и `/crosshair/<ник>` — отдельные страницы с title/description/canonical/H1, копирование кодов в один клик, предпросмотр прицела (для кодов формата `CSGO-…` и для прицела из конфига). Новый формат кода CS2 (`CS…`, 46 символов) копируется, но параметры из него не разбираются — картинка не рисуется. Связь с профилем игрока — по точному совпадению ника в CS2 (однофамильцы не угадываются); в профиле игрока появляется блок «Конфиг и прицел». Эти разделы работают и без сервера данных.

**Twitch только в CS2.** Блок «Сейчас в эфире» на главной показывается только при выбранной дисциплине CS2; на страницах матчей и турниров — только у CS2. Для Dota 2 и LoL блок не создаётся вовсе (проверка по типу игры в коде, не CSS). При смене дисциплины плеер останавливается, iframe удаляется.

# CyberLeague — часть 3 из 3: SEO и финальная проверка

**Что сделано**

- SEO-шаблоны всех страниц — `assets/js/seo-templates.js` (один модуль для браузера, Node.js-сервера и предгенерации): игроки, команды, матчи, турниры, конфиги, прицелы, разделы. Описание строится из реальных данных: прицел/настройки/биография упоминаются только если они есть; счёт — только у сыгранных и идущих матчей; трансляции — только если к матчу/турниру привязан канал; «актуальный состав» — только если профиль обновлялся за последние 45 дней.
- Страницы без ценности (матч с TBD, игрок без команды, матчей и конфига, команда без состава и матчей) получают `noindex` и не попадают в sitemap. Поиск, настройки, админка — `noindex`. Фильтры (`?status=…`) не создают отдельных canonical. Страниц под Twitch-каналы нет; эфиры не меняют адрес и canonical матча.
- Schema.org: `WebSite` (главная), `BreadcrumbList` (все сущности), `Person` (игрок), `SportsTeam` (команда). Без рейтингов, отзывов и выдуманных данных.
- **Видно без JavaScript.** Node.js-сервер подставляет title/description/canonical/OG/JSON-LD и H1 с хлебными крошками в HTML, отдаёт 404 для несуществующих объектов, `/sitemap.xml`, `/robots.txt`.
  Сайт без сервера (GitHub Pages): `scripts/prerender.js` в workflow создаёт отдельный HTML для каждой страницы (`/player/12/`, `/match/7/`, `/config/<ник>/` …) со своими метатегами, а также `sitemap.xml`, `robots.txt` и `404.html`. Адрес сайта для canonical берётся из настроек GitHub Pages (`SITE_URL`); домен не выдумывается.
- Проверка SEO: `npm run seo:check` (после `npm run prerender`) — одинаковые title, пустые description, некорректные названия, дубли canonical, индексируемые страницы без H1. Однофамильцы (один ник в одной игре) получают в title команду или имя.
- Старые адреса продолжают работать: `#/team/12`, `/crosshair` → `/crosshairs`.
- Исправлено: `.htaccess` запрещал отдавать любые `.json`, из-за чего на Apache-хостинге не загружался список Twitch-каналов (теперь закрыты только `package*.json`); на странице матча появился H1.

**Важно про хостинг ZIP.** Если `index.html` лежит на обычном файловом хостинге, страницы открываются через `#/…` — поисковики такие адреса отдельно не индексируют. Индексируемая версия — предсгенерированный сайт на GitHub Pages (или Node.js-сервер). Если у сайта будет свой домен, укажите его в `<meta name="site-url" content="https://ваш-домен">` в `index.html` и как `SITE_URL` в workflow.

**Запуск:** сервер — `cp .env.example .env && npm install && npm start`; проверки — `npm test`; без сервера — см. раздел «Сайт без сервера» ниже.

- Единственный источник данных — `assets/js/data/configs.js` (одна запись на игрока; профиль, конфиг и прицел берут её же). Сейчас записей нет: добавляйте только проверенные данные с источником. Поля, которых нет, не показываются.

**Twitch (без API-ключей и посредников)**
- Список каналов: `assets/js/data/streams-config.json` — 16 уникальных каналов (PGL один раз), группа `ru` (5 каналов) показывается первой, затем `other`. Порядок меняется только в этом файле: `group`, `priority`, `enabled`.
- Сайт **не использует Twitch API с ключами**: «в эфире» и число зрителей Twitch отдаёт сам по публичному запросу своего веб-клиента (`gql.twitch.tv`) — без секретов, своего сервера и посредников; ответ кэшируется на 60 секунд.
- Блок «Сейчас в эфире» показывает только каналы, которые ведут трансляцию в этот момент: слева — плеер, справа — меню эфирных каналов (название, язык, зрители, название трансляции). Если в эфире никого нет, блок скрывается целиком — вместе с плеером.
- Плеер открывается сразу на первом канале в эфире; переключение канала заменяет iframe в том же блоке (старый удаляется из DOM), страница не перезагружается.
- Служебные элементы самого Twitch не видны: шапка канала с «Отслеживать»/«Подписаться» и нижняя панель с «Клип», настройками и полноэкранным режимом вынесены за края кадра (`.player` в `assets/styles.css`: кадр больше видимой области на `--crop`, картинка при этом не режется — видео масштабируется с чёрными полями). Вместо них под плеером свои кнопки: «Включить звук» (официальные команды Embed) и «Во весь экран». На широких экранах блок растягивается на всю ширину страницы, поэтому плеер крупный.
- Встраивание работает только по HTTPS (требование Twitch); на http-сайте вместо плеера показывается ссылка на канал.

- Привязка канала к матчу/турниру (там же, `links`): `{ "login": "pgl", "tournament_id": 45 }` или `{ "login": "pgl", "match_id": 123 }` — привязанные каналы показываются первыми с пометкой «официальный канал». id турнира/матча — число из адреса страницы сайта.
- Проверка: `npm test` (tests/streams.test.js).

# Esports Hub — этап 4

## Сайт без сервера (GitHub Pages) — рекомендуемый способ

Сервер не нужен. Каждые ~15 минут GitHub сам забирает свежие матчи с BO3.GG и публикует обновлённый сайт.

**Настройка (один раз, ~10 минут):**
1. Зарегистрируйтесь на github.com и создайте **публичный** репозиторий (New repository → Public). Для публичных репозиториев всё бесплатно.
2. Загрузите в него содержимое архива: «Add file → Upload files», перетащите все файлы и папки (включая скрытую папку `.github`), нажмите «Commit changes».
   Если папка `.github` не загрузилась — создайте файл `.github/workflows/update-site.yml` вручную через «Add file → Create new file» и вставьте его текст.
3. Откройте **Settings → Pages** и в поле «Source» выберите **GitHub Actions**.
4. Откройте вкладку **Actions**, выберите «Обновление сайта» → **Run workflow**. Первый запуск идёт 5–15 минут.
5. Сайт будет по адресу `https://ваш-логин.github.io/имя-репозитория/` (ссылка видна в Settings → Pages). Свой домен подключается там же.

**Как это работает:** GitHub по расписанию запускает `scripts/update-data.js` — ту же синхронизацию, что и на сервере. Раз в час полная, в остальные запуски только текущие матчи.
Результат — один файл `data/esports.db`, который сайт открывает прямо в браузере. История матчей сохраняется: перед каждым запуском берётся база с опубликованного сайта.

**Статьи:** админ-панели в этом режиме нет. Статьи — это файлы `.md` в папке `content/posts` (образец — `_example.md`). Создайте или отредактируйте файл прямо на сайте GitHub — статья появится после следующего обновления.

**Ограничения:** live-счёт обновляется раз в ~15 минут (GitHub иногда задерживает запуски). Если в репозитории 60 дней не было изменений, GitHub приостанавливает расписание — тогда нажмите «Enable workflow» во вкладке Actions.

Вариант с Node.js-сервером (ниже) по-прежнему работает: если сайт отдаёт сервер, он сам использует API, а не файл.

Сайт статистики CS2, Dota 2 и League of Legends. Единственный источник данных — публичные страницы **BO3.GG**.

## Стек и почему
- **Node.js 18+ / Express** — backend и API.
- **SQLite (better-sqlite3)** — простая файловая БД, миграции в `migrations/`.
- **node-cron** — серверный планировщик (работает без открытого браузера).
- **HTML/CSS/JS без сборки** — `index.html` лежит в корне, как требует хостинг.

## Запуск
```bash
cp .env.example .env
npm install
npm run admin:create # создать администратора (логин и пароль спросит в консоли)
npm start            # http://localhost:3000 — миграции + первичная синхронизация + планировщик
npm test             # тесты (используют отдельную БД в памяти)
npm run sync         # разовая ручная синхронизация
```
Админ-панель: `/admin`. Пароли в исходниках не хранятся; в базе — только scrypt-хеш.

## Размещение на хостинге
Сайту **нужен хостинг с Node.js** (VPS, Render, Railway, Fly.io, панель хостинга с поддержкой Node.js).
1. Загрузите всю папку, выполните `npm install --production`, запустите `npm start` (или `node server.js`).
2. Сервер сам отдаёт `index.html` и `/api/*`.

3. За обратным прокси (nginx, панель хостинга) укажите `TRUST_PROXY=1` и `SITE_URL=https://ваш-домен`.

Если хостинг умеет только статические файлы, `index.html` откроется, но вместо матчей покажет сообщение «Backend API не найден».
Тогда запустите backend отдельно, пропишите его адрес в `index.html` (`<meta name="api-base" content="https://ваш-backend.example.com">`),
добавьте домен сайта в `CORS_ORIGINS` на backend и оставьте `.htaccess` (Apache) — он открывает `index.html` по прямым ссылкам вида `/team/12`.
**Админ-панель в таком режиме не работает** (cookie сессии строго привязана к одному домену) — для редактора статей нужен вариант, где Node.js отдаёт и сайт, и API.

### Файловый хостинг (сайт в подпапке, например `https://kotakniga.ru/0/29/`)
- `index.html` и `assets/` работают из любой папки: пути к файлам относительные, адреса страниц в этом режиме вида `…/0/29/#/team/12` (файловый хостинг не умеет открывать `index.html` по адресу `/team/12`).
- Если сервер данных не подключён, сайт показывает экран «Сервер данных не подключён» с инструкцией, а не ошибки в каждом блоке.
- Подключение: запустите этот же архив на хостинге с Node.js, в его `.env` укажите `CORS_ORIGINS=https://kotakniga.ru`, а в `index.html` на файловом хостинге — `<meta name="api-base" content="https://адрес-сервера">`.
- Админ-панель в этом режиме тоже работает: вместо cookie используется токен сессии в заголовке `Authorization` (хранится до закрытия вкладки и выдаётся только сайту из `CORS_ORIGINS`).
- Миграции базы хранятся в `migrations/*.js` (некоторые хостинги не принимают файлы `.sql`); в журнале `schema_migrations` они записываются под прежними именями `NNN_name.sql`, поэтому базы этапов 1–4 обновляются без повторов.

## API
`GET /api/games`, `/api/matches?game=cs2|dota2|lol&status=upcoming|live|finished&date=YYYY-MM-DD`, `/api/matches/:id`,
`/api/teams?game&q`, `/api/teams/:id`, `/api/players`, `/api/players/:id`, `/api/tournaments`, `/api/tournaments/:id`,
`/api/articles`, `/api/search?q=`, `/api/sync/status`.

## Источник данных и правила
- robots.txt BO3.GG запрещает `/api/` — к нему мы **не обращаемся**. Сервер читает robots.txt в начале каждой синхронизации и пропускает запрещённые пути.
- Читаются 9 публичных страниц (по 3 на дисциплину): `/matches/current`, `/matches/finished`, `/news`. Данные берутся из встроенного в HTML состояния страницы (`window.__NUXT__`), исполняемого в изолированной песочнице.
- Пауза между запросами (`REQUEST_DELAY_MS`), только одна синхронизация одновременно; CAPTCHA/403/429 не обходятся — ошибка пишется в журнал.
- robots.txt содержит `Content-Signal: ai-train=no, ai-input=yes, search=yes`. Публичных условий о повторной публикации данных не найдено; перед коммерческим запуском **получите письменное разрешение BO3.GG**.
- Логотипы показываются по оригинальным ссылкам `files.bo3.gg`; статьи — только заголовок, анонс и ссылка на оригинал.

## Этап 2 — подробные матчи

- Разбор страницы каждого матча (`/matches/<slug>`, `/dota2/matches/<slug>`, `/lol/matches/<slug>` — разрешены robots.txt). `/api/` BO3.GG не используется.
- Миграция `migrations/002_match_details.sql` применяется автоматически поверх базы этапа 1 (`npm run migrate` или при старте). Старые данные не удаляются.
- Новые таблицы: `match_games`, `match_game_sides`, `match_rounds`, `match_lineups`, `match_player_stats`, `match_team_stats`, `match_snapshots`, `sync_pages`.
- История: снимок (статус, счёт, счёт по картам/играм) пишется только при реальном изменении. События между проверками не восстанавливаются.
- Завершённые матчи перепроверяются, пока BO3.GG не закончит разбор (`parsed_status=done`), не более `DETAIL_MAX_ATTEMPTS` раз.
- Настройки: `DETAIL_LIMIT` (страниц матчей за цикл, 20), `DETAIL_MAX_ATTEMPTS` (6).

Новые маршруты API:
| Маршрут | Что отдаёт |
|---|---|
| `GET /api/matches/:id/full` | всё для страницы матча одним запросом |
| `GET /api/matches/:id/games?rounds=0\|1` | карты/игры, половины, раунды |
| `GET /api/matches/:id/lineups` | составы на матч |
| `GET /api/matches/:id/stats?game_id=` | статистика игроков и команд (`game_id=0` — итог матча) |
| `GET /api/matches/:id/history?limit=&offset=` | история изменений |
| `GET /api/matches/:id/players/:playerId` | статистика игрока в этом матче |
| `GET /api/matches?offset=` | пагинация, общее число — заголовок `X-Total-Count` |

Что реально публикует BO3.GG (проверено 25.10.2026):
- **CS2**: итог матча по игроку — K/D/A, ADR, KAST, хедшоты, первые убийства/смерти и прочие числовые поля (трейды, клатчи, мультикиллы, урон, экономика) в `extra`; рейтинг BO3 (собственная шкала BO3.GG, не HLTV). По картам — счёт, половины/овертаймы, каждый раунд (победитель, сторона, причина, длительность), рейтинг игрока на карте. Полной K/D/ADR по каждой карте на странице матча нет — она на подстраницах `/matches/*/*/*`, запрещённых robots.txt.
- **Dota 2**: по игре — победитель, счёт убийств, длительность; по игроку — герой, позиция, K/D/A, LH/DN, GPM/XPM, урон, net worth, варды; по команде — убийства, Рошаны, первая кровь/башня/Рошан, строения.
- **LoL**: по игре — победитель, счёт, длительность; по игроку — чемпион, роль, K/D/A, CS, золото, GPM, урон по чемпионам, KP; по команде — убийства, золото, башни, драконы, бароны, первые объекты.
- Пока BO3.GG не разобрал матч (`parsed_status=waiting`, игры `no_stats`), статистика остаётся пустой, и сайт прямо об этом пишет.

Тесты: `npm test` (13 тестов; фикстуры — урезанные реальные страницы BO3.GG в `tests/fixtures`).

## Этап 3 — профили и связи
Разделы: Команды, Игроки, Турниры (поиск, сортировка, пагинация), Рейтинги, Трансферы, Сравнение.
Профили загружаются постепенно: за цикл — до `PROFILE_LIMIT` страниц каждого вида, обновление раз в `PROFILE_TTL_HOURS`. Первый полный обход занимает несколько циклов.

## Этап 4 — портал, статьи и гайды, админ-панель

### Интерфейс
- Новый дизайн: тёмная графитовая тема, один акцентный цвет, шрифты с кириллицей (Unbounded, Manrope, JetBrains Mono), собственные компоненты: карточки и строки матчей, табло матча, KPI, таблицы, полосы и спарклайны.
- Настоящие адреса страниц (`/matches`, `/match/12`, `/team/5`, `/player/7`, `/tournament/3`, `/rankings`, `/transfers`, `/compare`, `/articles`, `/articles/<slug>`, `/search`, `/sync`, `/settings`, `/admin`). Старые ссылки `#/team/5` переадресуются автоматически.
- Главная: текущие, ближайшие и завершённые матчи, турниры, рейтинг команд по дисциплинам, статьи, новости BO3.GG, быстрый поиск с подсказками, состояние данных и время обновления. Все блоки — из `GET /api/home`.
- Переключатель CS2 / Dota 2 / LoL / Все — во всех разделах; выбор сохраняется в браузере (`/settings`).
- Пустые разделы показывают понятное состояние («ещё не загружено», «источник не опубликовал»), а не выдуманные данные.

### Обновление данных (не «реальное время»)
- Сервер опрашивает BO3.GG по `SYNC_CRON` (полный цикл) и `LIVE_SYNC_CRON` (только `/matches/current` и страницы live-матчей, не более `LIVE_DETAIL_LIMIT`; запускается, лишь когда есть live-матчи или матч начнётся в ближайшие 15 мин). Оба задания делят одну блокировку.
- Браузер периодически опрашивает API сайта (`CLIENT_POLL_SEC`, при live — `CLIENT_POLL_LIVE_SEC`), в фоновой вкладке опрос приостанавливается. Ответы API отдаются с ETag (`304`, если ничего не изменилось) и кэшируются в памяти на `API_CACHE_SEC`, кэш сбрасывается после каждой синхронизации.
- `GET /api/sync/freshness`: время последнего успешного обновления, `stale` (дольше `STALE_AFTER_MIN`), `source_ok`, последняя ошибка, расписание. Индикатор в шапке и предупреждения на главной: «идёт обновление», «данные устарели», «источник недоступен — показаны сохранённые данные».

### Статьи и гайды (собственный контент)
- Таблицы `posts`, `post_categories`, `post_tags`, `post_tag_links` (миграция `004_posts_admin.sql`).
- Публичный API: `GET /api/posts?q&kind=article|guide&category&tag&game&limit&offset` (X-Total-Count), `GET /api/posts/:slug` (+ похожие), `GET /api/post-categories`, `GET /api/post-tags`. Видны только опубликованные материалы с наступившей датой публикации.
- Markdown: заголовки (с оглавлением), жирный/курсив/зачёркнутый/выделение, ссылки, картинки с подписью, списки и чек-листы, цитаты, выноски `> [!TIP]` / `[!WARNING]` / `[!NOTE]` / `[!IMPORTANT]`, код, таблицы, разделители.
- Безопасность текста: рендер на сервере «сначала экранировать всё, потом разметка» — HTML автора не выполняется никогда; ссылки только http(s)/mailto/относительные, картинки только https или `/uploads/`; плюс Content-Security-Policy без inline-скриптов.
- Тексты BO3.GG не копируются: раздел «Новости BO3.GG» — только заголовки и анонсы со ссылкой на оригинал.

### Админ-панель (`/admin`)
- Вход по логину и паролю: scrypt (N=32768, соль 16 байт), сессия в HttpOnly + SameSite=Strict cookie (Secure при HTTPS), в базе — только SHA-256 токена; срок `SESSION_TTL_HOURS`.
- CSRF: каждое изменение требует заголовок `X-CSRF-Token` сессии; запросы с чужим `Origin` отклоняются. После `LOGIN_MAX_FAILS` неудачных попыток за `LOGIN_WINDOW_MIN` минут вход блокируется (по IP и по логину).
- Публикации: список с фильтром (черновики / опубликованные / отложенные) и поиском; редактор с панелью форматирования, предпросмотром (тот же серверный рендер), подсчётом слов, загрузкой обложки и картинок в текст (PNG/JPEG/WebP/GIF, проверка по сигнатуре файла, SVG запрещён), категориями, тегами, дисциплиной, адресом страницы, отложенной публикацией; сохранить / опубликовать / снять с публикации / удалить; Ctrl+S.
- Категории, ручной запуск синхронизации (полный цикл или текущие матчи), журнал запусков и ошибок, смена пароля (остальные сессии завершаются).
- Админ-API: `/api/admin/session|login|logout|password|overview|posts|posts/:id(/publish|/unpublish)|preview|uploads|categories|sync/run`.
- Создать администратора или сменить пароль: `npm run admin:create` (пароль вводится скрыто). Альтернатива — `ADMIN_USERNAME` + `ADMIN_INITIAL_PASSWORD` в `.env` для первого запуска (затем удалить).

### Поиск
`GET /api/search?q&type=teams,players,tournaments,matches,posts&game&status&date_from&date_to&limit` — команды, игроки, турниры, матчи (по командам и турниру), статьи; счётчики `totals`. Подсказки при вводе в шапке и на главной; страница `/search` с фильтрами. `GET /api/matches` получил `q`, `date_from`, `date_to`, `tier`.

### SEO
Сервер подставляет в `index.html` уникальные `title`, `description`, `canonical`, Open Graph для каждой публичной страницы, возвращает 404 для несуществующих объектов, для статьи сразу вставляет её текст (виден поисковикам без JavaScript). `/robots.txt` закрывает `/admin`, `/api/`, `/search`, `/settings`; `/sitemap.xml` — разделы, статьи, турниры, команды, игроки, матчи. Админка отдаётся с `X-Robots-Tag: noindex, nofollow`.

Тесты: `npm test` — 32 теста (этапы 1–4).
